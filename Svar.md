## Task 1 - mst
Based my implementation on Prim's algorithm, creating a priority-queue and hashset to check vertices and edges within the graph, and an arraylist of the correct edges to return. Since we were working with an entire graph, I created a variable to be the iterator over the vertices, and used that to add the edges and vertices to the priority-queue and hashset respectively. To work through every possible neighboring vertice from the starting edge, I used a while-loop. In this loop I used the poll function to retrieve and remove the first edge of the queue and checked if either vertice connected to it had been visited, and if not then add it. I also added the edge to the arraylist, and a check to add the adjacent edges of the non-visited vertices to the priority-queue. After the while-loop runs its course, the function returns the finished arraylist with the minimum spanning tree.

I had some challenges on the way though. Being a weighted graph, I knew that to get the least weight-costly tree I needed to have the priority-queue sorted correctly such that the poll-function in the while-loop would retrieve the lightest edge. I needed a comparator to do this, and ended up using the lambda-function to skip on creating a separate method. The lambda function uses the getWeight()- and compareTo()-functions to place the lightest edge first in queue, so the poll-function automatically picks the correct edge. In the loop itself, I first had the check from the class-notes to run the loop until the number of visited vertices reached the total number of vertices in the graph. This worked but it also meant creating a new variable, totalVertices, which needed a for-loop to add up. This meant adding extra runtime, so I changed the check to run until the priority-queue was empty. In theory, this improves the runtime, but in practice it was a bit slower on the tests (up to a 100ms each). This is because the priority-queue can still have edges in it even if every vertice has been visited. However, on larger trees it should in theory be faster.

## Task 2 - lca
Based my implementation of a breadth first search (BFS), using a similar methodology as the graph-search in lab 5. Using BFS, I first found all parent-vertices of the root and put them in a hashmap with a linkedlist serving as the queue. The hashmap is then returned, and used to find ancestors in the main method. I added the first vertice, u, and its ancestors to a hashset using a while-loop, and checked if the second vertice, v, was in the hashset using another while-loop. If it was, I would return it as the lowest common ancestor. If not, it would check all the ancestors of v until it found the lca. If neither v nor its ancestors were found in the hashset, I would return null.

I found making this method easier than the minimum spanning tree, as I already had experience with a BFS from lab 5 and I only needed to find a way to find ancestors of one vertice to check with another. I was only a bit stumped as to what to return if there was no common ancestor of u and v, but found out that this is theoretically impossible with the trees we are dealing with, so this value can be changed to anything as long as the method compiles (null in my case).

## Task 3 - addRedundant
Based my implementation of a similar methodology as the class PowerOutage (from the tests) to find the most vulnerable vertices, and then using heavy path endpoints to find the best vertices to create an edge between. Started by creating a hashmap for the size and hashset for visited vertices. Using a supporting metod, computeSubtreeSizes, I found the size of all the subtrees in the graph from the root with DFS and recursion. Then, I created a vulnerability-map as the size of the smaller of the two subtrees and put it into an ArrayList, using a TreeSet as an intermediary. With a while-loop, I did a binary search combined with finding the different path's heaviest endpoints to find the best vertices, bestA and bestB, to connect. This was done using another supporting method, heavyPathEndpoints, which constructs a subgraph of edges above the candidate vulnerability, finds the endpoints, and does a BSF on them, returning an object-array with the best vertices to connect.

This was definitely the most difficult task, and I had several previous attempts that did not work. One of my more successfull ones was to simply connect the middle point on each side of the tree, by doing a BFS on the entire tree, finding the farthest vertice on one side, create a path from that vertice to the other side, and connect the two middle points in the path. This passed some of the tests, but not all, most likely because it does not work well on assymmetric trees. I then had the idea to use PowerOutage as an inspiration for finding the sizes of subtrees, and in turn the damage done from removing certain edges. To then find the best vertices to connect, I was helped by generative AI to look for the heaviest endpoints. Though a bit complex, the method successfully finds the best vertices via the method explained above, and passes all the tests. Another thing to note is I used BFS for both the lca() and addRedundant() methods. I originally thought to have a separate supporting method for the BFS, but because the requirements are so different and the duplicate code is minimal, I decided against it in the final version.


# Runtime Analysis
For each method of the different strategies give a runtime analysis in Big-O notation and a description of why it has this runtime.

* ``mst(WeightedGraph<T, E> g)``: O(m log m)
    * The method mst() has a runtime of O(m log m). Creating all the variables has a negligible runtime of O(1). Adding the edges of the starting vertice to the priority-queue has a runtime of O(deg(startVertice) * log m). The methods in the while-loop are to remove and retrieve the first edge of the priority-queue with a runtime of O(log m) and to add the edges from the non-visited vertices using a for loop with the runtime of O(degree(nextVertice) * log m) a total of m times, giving a total of O(m log m) for the entire loop. This gives us a combined runtime of O(1 + degree(startVertice) * log m + m log m + degree(nextVertice) log m) = O(3m log m) = O(m log m).

* ``lca(Graph<T> g, T root, T u, T v)``: O(n + m)
    * The method lca() has a runtime of O(n + m). Creating all the variables has a negligible runtime of O(1). The for-loop for the BFS runs in O(degree(nextVertice)), which sums up to O(m) after the entire traversal, and each vertice is visited only once in the while-loop, with a combined runtime of O(n). That gives a total runtime of O(n + m) for the BFS. Finding the ancestors of u and checking against v also both have a runtime of O(n) for their while-loops. This gives us a combined runtime of O(1 + n + m + n + n) = O(3n + m) = O(n + m).

* ``addRedundant(Graph<T> g, T root)``: O((n + m) log m)
    * The method addRedundant() has a runtime of O((n + m) log m). Creating all the variables has a negligible runtime of O(1). Computing the sizes of the subtrees using computeSubtreeSizes() has a runtime of O(n + m). Creating the vulnerability-map uses a for-loop over all the edges in the graph, and has a runtime of O(m). Creating a treeset from the values in the vulnerability-map has a runtime of O(m log m) and putting it in an arraylist has a runtime of O(m), as does adding the later check in the arraylist (putting -1 at index 0). The method heavyPathEndpoints()in the while-loop to find the best vertices has a runtime of O(n + m), and the loop itself runs in O(m). The checks to find the farthest vertices using BSF if the best vertices are null, run in O(n + m) each. This gives us a combined runtime of O(1 + n + m + m + m log m + m + m + (n + m) log m + n + m + n + m) = O(3n + 6m + m log m + (n + m) log m) = O((n + m) log m).

* ``computeSubtreeSizes(Graph<T> g, T vertice, HashSet<T> visited, HashMap<T, Integer> size)``: O(n + m)
    * The supporting method computeSubtreeSizes() has a runtime of O(n + m). Checking if the input vertice has been visited and creating the variable for the size and putting it in the hashmap has a negligible runtime of O(1). The for-loop runs over all the neighbors of the input vertice, and itself has a runtime of O(degree(vertice)). The recursion has a runtime of O(n + m) after all the calls have been done, since it only visits every vertice once. This gives us a combined runtime of O(1 + n + m) = O(n + m).

* ``heavyPathEndpoints(Graph<T> g, HashMap<Edge<T>, Integer> vulnerability, Integer k)``: O(n + m)
    * The supporting method heavyPathEndpoints() has a runtime of O(n + m). Creating all the variables has a negligible runtime of O(1). In the for-loop, putting all the vulnerable edges in the graph has a runtime of O(1), but the loop itself runs over all the edges in O(m). The  for-loop for checking all the entries in the hashmap runs in O(n) since it only checks the vertices, and every method within the loop runs in O(1). The BFS uses similar logic as in lca() and runs in O(n + m). This gives us a combined runtime of O(1 + m + n + n + m) = O(2n + 2m) = O(n + m).

**n = number of vertices, m = number of edges
